# LibreWheel architecture

LibreWheel targets the Logitech G29 in native USB identity `046d:c24f` on Windows. Windows continues to enumerate the wheel and deliver inputs through its inbox HID transport and class drivers. Games keep the physical DirectInput identity and receive its steering, pedals, and buttons. For DirectInput force feedback, the candidate is a user-mode `IDirectInputEffectDriver` COM DLL associated with that product through `OEMForceFeedback`. The x86 DLL serves 32-bit games running on x64 Windows. DirectInput provides the exact device interface in `DIHIDFFINITINFO`, allowing the DLL to verify and open the corresponding joystick collection.

- A UMDF transport minidriver would duplicate working USB HID transport and would still need to expose standard PID effects or use the OEM effect interface. A filter would add installation risk while solving neither effect translation nor session lifetime on its own.
- A standard HID PID device could support consumers that require PID reports. Providing an additional PID identity would require an emulated device or a descriptor-translating transport. Microsoft VHF currently requires a kernel-mode source, with Windows kernel signing and distribution requirements. Consider this route if physical device registration fails on supported Windows builds or if a required game bypasses the DirectInput OEM extension.
- The OEM DLL can be built with the Windows SDK. No WDK, custom kernel driver or kernel test signing is required for this design.

References: [DirectInput effect driver](https://learn.microsoft.com/en-us/windows/win32/api/dinputd/nn-dinputd-idirectinputeffectdriver), [HID device initialization ABI](https://learn.microsoft.com/en-us/windows/win32/api/dinputd/ns-dinputd-dihidffinitinfo), [inbox HID transports](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/transport-minidrivers), [Virtual HID Framework](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/virtual-hid-framework--vhf-), [G25 Windows implementation](https://github.com/hicwic/g25-w11-driver).

## Evidence for the G29

The tested G29 booted as `046d:c294` revision `1350` with the selector set to PS3. LibreWheel checks the shared product ID, the G29 revision family, and the unnumbered vendor output field before sending the two mode-switch reports. The wheel then appeared as `046d:c24f` revision `8900`. Its `MI_00` interface used `input.inf` and `HidUsb`, with 13-byte input and 17-byte output buffers in the Win32 HID API. Windows exposed four axes, 25 buttons, and one POV on that physical device.

Independent descriptor observations identify an unnumbered joystick report on `MI_00` with a four-bit hat, 25 buttons, 16-bit X steering, and three eight-bit pedal values. The classic output field is vendor usage `ff00:02`, 16 payload bytes. The Win32 HID API adds a report-ID byte of zero for unnumbered reports. The seven-byte command is zero-padded to that output field. Actual motor direction is still a bench test. The G29 shares classic Logitech protocol behavior with older wheels, whose descriptors and mode-switch procedures can differ. The force-feedback transport accepts only the native joystick collection.

References: [G29 descriptor capture](https://github.com/AprilNEA/OpenLogi/issues/16), [G29 HID report observations](https://github.com/karrvel/g29-mac/blob/main/_knowledge/gotchas/lg4ff-reports-must-be-16-bytes.md), [SDL G29 support](https://github.com/libsdl-org/SDL/blob/main/src/joystick/hidapi/SDL_hidapi_lg4ff.c), [Win32 HID report writes](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/sending-hid-reports).

Linux `hid-lg4ff` supplies reference evidence for constant-force download/play, stop, autocenter disable and rotation range. `new-lg4ff` shows that the classic wheel has limited hardware slots and that periodic and ramp effects can be mixed on the host. Older-wheel experiments are supporting protocol context. LibreWheel implements its own effect scheduler, conditions, interpolation, host integration and report encoding based on documented API and observed wire formats. It contains no Linux driver source.

References: [Linux hid-lg4ff](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-lg4ff.c), [Linux mode switching and range](https://docs.kernel.org/admin-guide/abi-testing.html), [new-lg4ff](https://github.com/berarma/new-lg4ff), [classic wheel protocol experiments](https://wiibrew.org/wiki/Logitech_USB_steering_wheel).

## Effects and shutdown

DirectInput effect parameters enter a single-axis software evaluator. Constant, ramp, periodic and spring effects can be evaluated from effect time and wheel position. Damper, friction and inertia depend on timed steering samples and need calibration and bench verification before advertising their capabilities. Host mixing permits a single correction curve at the summed actuator output. Per-effect gain applies before summing. Device gain and the user's gain apply to that sum before clipping to the LUT input domain. The optional LUT then adjusts the absolute force and retains its sign. Finally the report encoder quantizes and bounds the command.

DirectInput specifies the source of a force. For single-axis constant force, the SDK's Cartesian example uses direction zero and a signed magnitude. LibreWheel interprets a positive magnitude in that form as a pull toward decreasing steering counts. The HID encoder takes physical torque in steering-axis coordinates. Spring torque comes directly from the signed displacement, so positive spring coefficients still oppose the displacement. [DirectInput effect direction](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417536(v=vs.85)) · [DirectInput SDK sample](https://github.com/walbourn/directx-sdk-samples-reworked/blob/main/DirectInput/FFConst/ffconst.cpp)

The classic constant-force slot can retain its last command. A hardware-output build launches an output owner when the mixer first has nonzero force. The output owner waits for the game process, a stop event and a time-limited mailbox update. On shutdown it attempts to stop the slot, retrying failed stop writes. The bench build limits the classic force byte and the full-force test build uses its native range. Both use the same output owner. The default build operates without motor output. A host-side cleanup path requires a working host and USB bus. Broader use depends on verifying the transport, stop behavior and loss-of-host behavior with hardware. A bounded firmware effect or narrowly scoped cleanup driver are candidates if physical testing identifies a gap.

## Tray idle behavior

The tray waits in the Windows message loop. It receives HID arrival notifications on its window and starts a short-lived worker for a compatibility-mode G29 so the mode switch can wait for re-enumeration. It scans for LUT files when the tray menu opens. [Win32 device notifications](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerdevicenotificationw)

## MSVC profile-guided builds

Configure a Release build with `-DLIBREWHEEL_PGO_MODE=TRAIN` to build an instrumented `LibreWheelFF.dll`. Exercise the DLL with a representative workload and let it unload to save the profile counts. Reconfigure the same build with `-DLIBREWHEEL_PGO_MODE=USE` and rebuild. CMake enables link-time optimization and applies the driver profile. The profile database defaults to `LibreWheelFF.pgd` in the build directory and can be set with `LIBREWHEEL_PGO_PROFILE`. Each architecture needs a profile from its own build, using the same toolset and compiler options. [Microsoft's PGO workflow](https://learn.microsoft.com/en-us/cpp/build/profile-guided-optimizations?view=msvc-170)

`Build-Installer.ps1` accepts `-PgoProfileX64` and `-PgoProfileX86` for a profiled release. Train those profiles with the matching `full-force-x64` and `full-force-x86` Visual Studio presets so the compiler and linker options agree with the installer builds. Keep the training runtime and generated profile data in the build workspace.
